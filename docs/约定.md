## 一、需求怎么改（用户 2026-10-03 定）

**一句话：需求的任何增删改，都要同步进文档；PRD 是需求的唯一来源。**

用户会零碎地提需求（试用反馈、一句"能不能…"、一个优化点）。这些都是需求变更，
**必须落到 [PRD](PRD.md)**，不能只活在某份状态报告或交接页里。

### 变更时逐项做这些（缺一项就是没同步完）

| # | 变更类型 | 要做的事 |
|---|---|---|
| 1 | **新增需求** | PRD §3 追加 FR 编号（**新增用 `FR-7.x` 递增，不动已有编号** —— 代码注释/STATUS/验收脚本都在引用）。写清：**行为 + 用户原话或为什么 + 验收怎么看**。同时注明日期 |
| 2 | **修改需求** | 改对应 FR；**被推翻的原文划掉并注明更正**，不静默改写 |
| 3 | **删除 / 砍掉需求** | 划掉原文 + 注明"为什么砍、谁定的"，**不要整条删掉** —— 否则下个会话会把它当新需求再加回来 |
| 4 | **行为变了** | 更 §8 验收标准：新增/修改 AC 编号，写清**验证方式**（单测 / 仪器测试 / 模拟器 / 真机 / 肉眼） |
| 5 | **做了取舍** | §10 决策点追加一行（取值 + 理由） |
| 6 | **功能做完** | `M?-STATUS.md` 记实现与证据；更新 [STATUS](STATUS.md) 的基线数字或 bug 台账 |
| 7 | **要真机/耳朵验的** | 同步 [点检清单](MACHINE-CHECKLIST.md) 与 [交接-剩余工作](交接-剩余工作.md) |
| 8 | **悬置的问题** | 同步 [交接-剩余工作](交接-剩余工作.md) §3「待用户拍板」 |
| 9 | **还没定的（不是需求）** | 挂到 **PRD §3 末尾「待拍板（定了才落成 FR）」**表。**没定之前不实现** |

### 关于 PRD 的三条维护约定

1. **不动已有编号**（新增一律 `FR-7.x` 递增）；
2. **被证伪的说法划掉并注明更正**，不静默改写；
3. **改了行为就回来改 PRD**，并补 §8 的验证方式。

## 二、怎么验证（改完必须能复现）

**基线数字**（改完必须复现同样的数字，变了就要在交接文档里说明并更新基线）：

| 项 | 值 | 命令 |
|---|---|---|
| JVM 单测 | **102**，0 failures | `cd android; gradle :app:testDebugUnitTest` |
| 仪器测试 | **29**（`MigrationTest` 3 / `AlarmRepositoryTest` 17 / `AlarmSchedulerTest` 6 / `ShellSmokeTest` 3） | 见 [STATUS](STATUS.md) §3 第 6 步 |
| 调度端到端验收 | **5/5** | `.\tools\m3-acceptance.ps1` |
| 乱码检查 | clean | `python tools\check-encoding.py` |

> 仪器测试从 28 变成 29，是因为 PRD FR-7.10 的迁移 v3→v4 加了一条迁移测试
> （`migratingFrom3To4AddsThePreAlertColumnWithoutClaimingAnythingWasAnnounced`）。
> **数字变大也要写在这里** —— 否则下个会话会以为"基线是 28"，把新增的测试当成异常。

**四条硬规矩**：

1. **验收脚本也会说谎。** 每条断言都要能对着**原始日志/原始输出**核对。历史上脚本给过十几次假失败，
   产品每次都是对的。看到失败先问"是产品错了还是我在说谎"。
2. **不要断言"用户数据是空的"。** 仪测与应用共用数据文件，那种断言测的是用户干了什么，不是 schema。
3. **工具在一台设备上验过 ≠ 验过。** 修工具（尤其是 CDP/探针类）必须在**模拟器和真机**各验一次 ——
   `ui-drive.eval()` 的修复就只在模拟器上验证过，到真机三条 UI 测试全红（`STATUS.md` §1.1 #24b）。
4. **凡是靠手势才存在的交互，验收必须用手势。** 点击只能证明另一半。

## 三、怎么写文件（这台机器的编码坑）

1. **源码/文档只用编辑工具读写，绝不经过 shell 文本管道。** 本机控制台是 GBK 代码页，
   `Get-Content`/`Set-Content` 往返会把 UTF-8 中文毁成乱码，且不可逆（`STATUS.md` §1.1 #18）。
2. **`.ps1` 脚本里的中文字符串必须存成「UTF-8 with BOM」。** 这台机器只有 Windows PowerShell 5.1，
   它用 ANSI(GBK) 代码页读脚本；没有 BOM 时中文**字符串**会被拆成语法错误（注释里则只是难看）。
3. **不要用 heredoc**（`<<'EOF'`）—— 这台 shell 不支持。要写脚本就写成文件。
4. **给 git 的中文（如提交信息）必须有 BOM 或走文件**，否则会变成乱码提交信息（`STATUS.md` §1.1 #26）。
5. **改完跑 `python tools/check-encoding.py`。** 它认两种东西：U+FFFD，以及"能被 GBK 误读还原"的片段。
   要**引用**乱码当例子时，在那一行或该文件加 `encoding-check: allow`（可 grep 审计）。

## 四、怎么提交（用户 2026-10-02 定）

**每完成一个比较重要的节点，就推一次仓库，不要攒到最后。**

```powershell
. .\tools\env.ps1
.\tools\push.ps1 -Message "M9: 上滑关闭闹钟（真机 28/28）"     # 加 -WhatIfOnly 只看清单
```

`tools/push.ps1` 四道检查：乱码 → 列出将提交的文件并**拒绝**缓存/构建产物/密钥/第三方二进制 →
提交 → 推送并核对远端 HEAD 一致。

* 分支固定 **`master`**（用户习惯，别改 `main`）；
* 提交信息写 **"做了什么 + 怎么验证的"**；
