## 3. 第 2 项：长按批量勾选删除（已完成）

### 3.1 做了什么

- **契约加了一个方法**（M6 之后第一次扩契约，属增量、不改动既有方法）：

  ```ts
  deleteAlarms(o: { ids: number[] }): Promise<{ affected: number }>
  ```

  为什么不循环调用 `deleteAlarm`：每次写操作都会 `recomputeAll()` 把整个调度表重新注册一遍
  （DEVELOPMENT-PLAN §M6.4），删 20 条就要重算 20 次；而且中途失败会留下"删了一半"、
  用户无法判断哪一半成功了的状态。

- **列表页**：长按任一行进入选择模式；每行出现勾选圈；顶部变成「✕ / 已选择 N 项 / 全选」；
  底部出现固定的「删除」；删除是**两步确认**（第一次点变成「确认删除 N 项？」，第二次才真删），
  和「清理已过期」「删除分组」保持同一套交互。

- **长按的实现**（`AlarmRow.vue`）：`pointerdown` 起 450ms 计时器（等于 Android 自己的
  `ViewConfiguration.getLongPressTimeout()`），手指移动超过 12px 就取消（那是在滚动），
  触发时震动 12ms 作为反馈，并吞掉长按之后浏览器补发的 `click`。

### 3.2 测试过程中抓到的两个真 bug

**① 长按会勾错行（严重，真机上一样会发生）**

第一版把选择栏**替换**掉了大时钟 —— 而大时钟约 300px 高。于是进入选择模式的**那一瞬间整个列表向上跳**，
可长按还在进行中：手指原地不动，浏览器在抬指时补发的 `click` 就落在了"跳上来"的另一行上。
测试表现为「长按 1 行，勾中了 2 行」。

修法：选择栏改为**覆盖**在大时钟之上（`position: absolute; inset: 0`），大时钟留在布局里，
权限提示条也不再隐藏 —— **列表上方任何东西的尺寸都不再变化**。回归断言直接钉住这个不变量：

```
the long-pressed row: y=502.796875 before, y=502.796875 after      ← 真机
hero rect=[0, 0, 400, 208]  selection bar rect=[0, 0, 400, 208]    ← 完全重合
```

**② 底部固定操作栏盖住了最后一行**：`position: fixed` 的栏浮在列表上，最后一行点不到。
修法是给页面在选择模式下加 112px 底部留白，让它能滚出来（和 Gmail 的选择栏同一套办法）。

## 4. 第 3 项：滚轮循环滚动（已完成）

### 4.1 你给的参考就是答案

你截的小米闹钟里，小时列是 `…21 22 23 00 01…`、分钟列是 `…57 58 59 00 01…` —— 首尾相接。
原来的实现在 23 或 59 就**停住了**。

### 4.2 实现

每列渲染 **3 份相同内容**，滚出中间那份时静默挪回中间：

```ts
const COPIES = 3
const MID_COPY = 1
// 逻辑值 = domIndex % count；回中把 domIndex 加减一个完整的 count，取模不变
// ⇒ 回中永远不会改变选中值 ⇒ "滚动处理函数被自己的修正再次触发"这个经典死循环在这里不可能发生
```

**回中只在滚动停止后（140ms 无滚动）执行**，不在滚动过程中：手势进行中改 `scrollTop` 会被浏览器
用触摸位移覆盖掉，而在惯性动画中改会让剩余的惯性从一个与合成器不同的原点继续。

### 4.3 一条必须钉住的不变量

高亮（`aria-selected`）按**逻辑值**标记，所以三份里各会标一个 —— 但三份相距整整一列，
**任意时刻只有一份在可视区内**。测试直接验这一点，因为"高亮的不是居中那行"意味着
**用户看到的和保存下去的不是同一个值**：

```
[OK ] the value is marked in every copy: 3
[OK ] but only one of those is on screen: 1
[OK ] and it is the centred row: '06'
```

### 4.4 证据

`.shots/t-wheel.py`，模拟器与真机各一遍全绿。真机原文：

```
  after one row past 23: centred='00' onScreen=['22', '23', '00', '01', '02']
[OK ] one row past 23 is 00, not a stop: '00'
  after one row before 00: centred='23' onScreen=['21', '22', '23', '00', '01']
[OK ] one row before 00 is 23, not a stop: '23'
[OK ] a 48px drag advances exactly one hour: 7
  values seen while spinning forward: ['01', '02', ..., '10']
  last six: ['11', '12', '13', '14', '15', '16']
[OK ] thirty single steps from 10 stayed a clean mod-24 walk: ['11', ..., '23', '00', '01', ..., '16']
[OK ] three rows past 58 is 01: '01'
[OK ] and three rows back is 58 again: '58'
```

**连走 30 格、跨了两次边界、一次没卡、每一步都恰好 +1** —— 这是"循环且不会用完"最强的证据。

M6 之后已经做过的三件事（`WheelTimePicker.vue` 顶部注释里有完整记录）：`scroll-snap-stop: always`

## 8. 第 2 轮补充（第 1 项的缺口 + 第 4 项的第三个借鉴）

### 8.1 在编辑闹钟时直接新建分组（第 1 项的缺口，已完成）

原来想在设闹钟时建一个「吃药」分组，只能退出去到 **设置 → 分组管理** 建好再回来选 —— 于是分组列表
就不会长出来。现在分组那一行末尾有一个虚线框的「＋ 新建」，点开是一个内联输入框（不弹层、不跳页）：

- **不选颜色**：用户来这里是为了打名字，所以自动取调色板里下一个颜色，之后可在分组管理里改。
- **输入已存在的名字 = 选中它，而不是建一个重名**：同一个分组不该有两行。
- 失败会红字显示（和保存闹钟同一条规矩：绝不静默失败）。

### 8.2 编辑页顶部的相对时间预览（第 4 项的第三个借鉴）

小米闹钟标题下面那行「6 小时 35 分钟后响铃」。它回答的是这个页面**最容易犯的错**：时间和日期选对了、
但日子选错了（明天还是后天）。

**它必须由原生算，不能在网页里算**：重复规则、节假日日历、暂停下限都是业务规则，TECH-STACK §3 要求它们
留在 `domain/`。所以加了一个纯预览方法（照 `previewPause` 的先例）：

```ts
previewNextRing(o: Partial<Alarm>): Promise<{ nextRingAt: number | null }>
```

**第一版是错的，而且错得有意义。** 它只调了 `newAlarm()`，于是新建的「单次」闹钟因为没有 `onceDate`
（那个字段是**保存时**回填的）而显示「**不会响铃**」—— 一条单次规则没有日期就永远不匹配任何一天。
预览必须和保存走**同一条**计算路径，否则它就是在骗人；修法是加上保存路径也在用的 `backfillOnceDate()`。

还有一处竞态：每动一下滚轮就发一次请求，**响应会乱序**，所以页面用一个自增代号守着 —— 只有最新一次的
结果才允许写进那一行。否则快速旋转之后，那行会停在一个比滚轮更早的值上，比不显示更糟。

### 8.3 「时 / 分」列标签：~~有意推迟~~ **已完成**（第 4 轮）

> **上一轮的结论与更正。** 第 2 轮我把它记为「有意推迟」，理由是：`.col` 是 `block-size: 100%`，
> 而 `.wheel` 是固定 240px（5 行 × 48px），往里加任何一行都会把滚动区压矮，而"居中那行即选中那行"
> 与 `round(scrollTop / 48)` 都建立在**行高整除可视高度**上；要安全地做就得动一个刚刚验证过手势的
> 组件，而当时没有余量改完再完整重验一遍。
>
> **第 4 轮做完了，因为余量来了**（手机掉线，真机验证做不了，正好做这件只在模拟器上就能验的事）。
> 做法正是上一轮判断的那条路：给每列包一层 `.colwrap`，标签**绝对定位在列上方、落在 `.wheel` 的
> 上内边距里**（`--wheel-head-h: 18px`），于是列的高度**一点没变**。绝对定位子元素是相对**内边距盒**
> 定位的，所以两端渐变和选中带都必须按 `--wheel-head-h` 偏移 —— 漏掉这一步，选中带就会偏离中间那一行。
>
> 几何实测（模拟器）：
>
> ```
> wheel   [116,  90, 180, 258]   ← 18px 标签 + 240px 列
> col     [116, 108,  84, 240]   ← 高度仍是 240px
> head    [116,  90,  84,  18]   ← 「时」正在列正上方
> band    [138, 204, 137,  48]   ← 中心 228 = 列中心 228（108 + 120），没偏
> ```
>
> 然后**用手势测试整套重验**（这才是上一轮推迟它的理由，所以必须补上）：
> `.shots/m8-wheel-emulator.txt` → **ALL CHECKS PASSED**，包含最依赖几何的那条

### 8.4 工具链这一轮补的两处（都源于真 bug）

| 问题 | 修法 |
|---|---|
| `Runtime.evaluate` 里的**顶层 `await` 是语法错误**，而我的工具把异常对象截成 `"{"` 返回，看起来像正常值 —— 于是"脚本坏了"和"脚本通过了"长得一模一样 | `ui-drive.py` 解析**整段**输出（不再只看第一行），并在结果是 `{__exception: …}` 时**抛错**。这样表达式写错会立刻炸，而不是静默地什么都不做 |

### 8.5 一键真机验证（第 5 轮新增）

真机验证原来是手敲的一串步骤，而每一步都有一种"悄悄错掉"的方式：

- **包可能是旧的** —— Gradle 构建失败时磁盘上留的是上一次的 APK，测试就会去验一个不是当前代码的包。
  所以脚本重跑构建，并在安装后用 **SHA-256 逐字节比对**（时间戳比对曾经骗过我们：构建失败时
  `lastUpdateTime` 会和旧构建对上）。
- `adb forward` 的名字里带 pid，应用重启就失效；手机上 MIUI 会自己重启它。
- 手机熄屏会让 MIUI 挂起 WebView，DevTools socket 当场消失。
- 测试会写用户的真实数据库，所以"有没有弄坏"必须**被验证**而不是被假设。

`tools/verify-phone.py` 把这些收在一处：先判断手机在不在 adb 上（**并区分"线没插好"和"USB 模式不对"**，
后者在 MIUI 上最常见），再构建+安装+哈希比对，再记录前后的闹钟/分组条数，再逐个跑 UI 测试并存证，
最后给一张 PASS/FAIL 汇总。用法：

```powershell
python tools\verify-phone.py            # 全流程
python tools\verify-phone.py --skip-build
```

**它的失败分支也验过**：手机不在 adb 上时，它打印 Windows 是否看得到设备并给出三步手机侧操作，
退出码 2（`--skip-build` 之外的分支不会静默通过）。

顺带修正了测试里三处**我自己的错误期望**（都不是产品问题）：
- 「一次 144px 拖动正好走 3 格」—— 实际带惯性会走 2~4 格；断言改成 1~4 小时区间。
- 「组数在建组后正好 +1」—— 写操作经过协程 + 全量重算，读库要轮询。
- 倒计时按分钟取整，两次读数差 1 秒，所以"正好 3 小时"不可达 —— 给了 ±90 秒余量。

**规律**：这三条都是"我把测试的期望写死成一个理想值"。产品是对的，测试太自信。

### 9.1 那个死循环的成因（值得记，因为它和"侧滑正常"是同一个原因）

```html
<GroupsPage      @back="go({ name: 'settings' })" />   <!-- 错：go() 是**压入**一条新记录 -->
<PermissionsPage @back="go({ name: 'settings' })" />
```

`go()` 压栈、`back()` 出栈。用 `go()` 当返回键，就会在栈里留下一条重复的"设置"记录：
设置 →(压) 分组管理 →(返回却再压一次设置) → 设置 →(这次真出栈) → 退回**上一条分组管理记录** → 死循环。

**侧滑之所以正常，正是因为它走的是 `back()`**，从来不压栈。所以"手势对、按钮错"这个组合本身就是线索：
两者本该走同一条路，走岔了就说明有一边用错了 API。修法是把两处都改成 `@back="back"`，
层级关系不受影响（分组管理是从设置进去的，出栈自然回到设置）。

### 9.2 第 3 条的一个自我更正

第一版把**所有 `isSystem` 分组**都钉在最前，于是「工作日」「节假日」也被顶上去，真实分组（吃药）被挤到最后 ——
比要求多做了，而且做错了。现在**只钉「未分组」**。默认选中同理：原来是"按 sortOrder 的第一个"，
所以把「工作日」排在前面的用户，新建的闹钟会**悄悄被归到工作日**；现在固定默认「未分组」。

**真正测到"钉住"逻辑**：用户当时的排序里「未分组」本来就在第一位，所以 pin 分支**根本没被触发过** ——
只测"顺序正确"是个假阳性。于是把分组管理改成以「吃药」开头再验：

```
分组管理顺序:  吃药 → 未分组 → 工作日 → 节假日 → M3 TEST
列表页:        吃药   未分组   工作日   节假日   M3 TEST     ← 完全跟随分组管理 ✅
编辑页:        未分组←选中  吃药  工作日  节假日  M3 TEST     ← 只钉未分组，其余仍跟随 ✅
```

两边**必须不一样**才能证明钉住生效，而它们确实不一样。测完已还原顺序。

### 9.3 返回这件事的完整模型（第 4 条）

按安卓的返回栈语义实现，而不是"返回就跳列表"：

```
选中模式  →  上一层页面  →  根页面才退出应用
```

- **每一层可返回的状态都压一条历史记录**（页面跳转、进入选择模式），所以侧滑手势、返回键、
  以及我们自己的 ✕ / 取消按钮**走的是同一条路**，不可能互相矛盾。
- 原生侧**问页面自己的状态**（`window.__dshCanGoBack` / `__dshBack`），不问 `WebView.canGoBack()`。
  后者与页面的状态会脱节：应用切到后台再回来时 Chromium 可能换掉 renderer，原生据此得出
  "没有可返回的" 就会 `finish()` —— 表现是**从设置页返回却退出了应用**。

### 10.1 AC-9 的更正：我把"慢"当成了"失败"

M8 期间我曾判定「AC-9 重启后重注册**失败**」。**那个结论是错的，在这里划掉：**

> ~~「AC-9 重启后重注册失败」~~

两条真因，都是我的观测方法的问题：

1. **观测窗口只有 8 秒。** HyperOS 上 `BOOT_COMPLETED` 是**延迟投递**的 —— 实测重启后约 **60 秒**
   应用才被拉起、注册才回来。8 秒时去看，看到的必然是什么都没有。
2. **第一次测还叠加了我自己造成的 stopped 状态。** 我先跑过 `am force-stop`，
   而处于 stopped 的应用**收不到任何广播，包括开机** —— 那次"没注册"是我自己造出来的。

更正后的结论：**重启后重注册是好的，只是慢（约 60 秒）**；唯一真实的缺口是那 60 秒窗口内到期的闹钟会漏掉，
这是平台行为，不是我们能修的。
