## 1. 项目概述

### 1.1 一句话定位

一个**能按场景给整组闹钟一键放假**的本地闹钟：把闹钟按「工作日 / 节假日 / 自定义场景」分组，请假时一键暂停整组 N 天并自动恢复；一次性提醒闹钟默认用完即删。

### 1.2 要解决的问题

系统自带闹钟（含小米闹钟）有两个痛点：

1. **没有分组，无法整组暂停。** 工作日设了 3 个闹钟（起床上班、出门、午休结束），请假时必须一个个手动关掉，第二天再一个个开回来。忘记恢复会导致迟到，忘记关闭会导致休假被吵醒。
2. **一次性闹钟会无限堆积。** 用闹钟提醒「10 分钟后取快递」「晚上给客户回电话」，时间久了列表里全是过期哑闹钟。自带的「响铃后删除」每建一个都要手点一次，无法设默认。

### 1.3 目标用户与核心场景

只有一位用户（本人），日常场景：

| 场景 | 期望行为 |
|---|---|
| 周一早上决定今天请假 | 点「工作日」组的暂停 → 选 1 天 → 组内 3 个闹钟今天全部不响 → 明早 00:00 自动恢复 |
| 连休 3 天 | 点「工作日」组暂停 → 3 天 → 跳过接下来 3 个工作日，第 4 天恢复正常 |
| 国庆调休的周六要上班 | 「工作日」组在调休上班的周六**照常响铃**，法定假日的工作日**不响** |
| 随手建个 20 分钟后的提醒 | 建完就不用管了，响过之后自己消失，不堆积 |
| 休假结束忘了恢复 | 不会发生——临时暂停到期自动恢复 |
| 整理历史遗留的一堆一次性闹钟 | 设置里一键把它们全标记成「响铃后删除」 |

### 1.4 非目标（明确不做）

**v1 不做**，避免范围失控：

- 睡眠监测、天气、世界时钟、秒表 / 计时器、音乐播放器、白噪音
- 账号体系、云同步、多设备同步、社交分享
- 网络请求、埋点统计、广告、崩溃上报（**App 不申请 `INTERNET` 权限**）
- 桌面小组件（Widget）
- 法定节假日免打扰开关（与「分组暂停」功能重叠）
- 配置的备份导出 / 导入（换机需重新配置）
- 「每 N 天」重复、按农历重复
- 语音控制、AI 智能建议

## 2. 术语定义

| 术语 | 含义 |
|---|---|
| **分组（Group）** | 一组闹钟的集合，是暂停操作的**最小单位**。每个闹钟**只能属于一个分组**。 |
| **响铃日（Ring Day）** | 某个具体日期，某闹钟按重复规则本该响铃。工作日组若每周一~五 07:00 响，则一周有 5 个响铃日。 |
| **跳过 N 个响铃日** | 暂停语义。跳过未来 N 个本该响铃的日期，恢复时刻 = 第 N 个响铃日的次日 00:00。详见 §5.3。 |
| **临时暂停** | 有明确恢复时刻的暂停，到期自动恢复。 |
| **永久停用** | 无期限的关闭，必须手动恢复。 |
| **一次性闹钟** | `repeatType = ONCE` 的闹钟。 |
| **过期闹钟** | 已响过、且未勾选「响铃后删除」的一次性闹钟。不会再次响铃，但留在列表里。 |
| **响铃时刻二次校验** | 闹钟被系统唤醒后、真正发声前，再查一次数据库确认是否处于暂停/停用状态。详见 §5.4。 |

## 3. 功能需求

| 编号 | 需求 | 优先级 |

| FR-1.2 | 内置 3 个分组：**未分组**（默认，不可删除）、**工作日**、**节假日** | P0 |

## 5. 关键业务规则

### 5.1 下次响铃时间计算

输入：闹钟 + 节假日数据 + 当前时间 + 生效的暂停状态。

```
若 闹钟.enabled = false           → 无下次响铃
若 闹钟.permanentlyDisabled        → 无下次响铃
若 分组.permanentlyDisabled        → 无下次响铃
否则，从「今天」开始向后逐日检查，返回第一个满足以下全部条件的 (日期, 时分)：
    a) 该日期匹配重复规则（见 §5.2）
    b) 该日期时间点 > 当前时间
    c) 若存在临时暂停，则该时间点 > max(闹钟.pauseUntil, 分组.pauseUntil)
```

若 366 天内无匹配（例如 `WEEKLY` 但没选任何星期），视为「永不响铃」并在编辑页给出校验错误。

### 5.2 重复规则匹配

| `repeatType` | 匹配条件 |
|---|---|
| `ONCE` | 日期 == `onceDate`；`onceDate` 为空则取「下一个到该时分的日期」并在保存时写入 |
| `DAILY` | 每天 |
| `WEEKLY` | `repeatDays` 对应该星期几的位为 1 |
| `WORKDAY` | 该日是法定工作日：周一~周五**且非**法定节假日，**或**是调休上班日（含调休的周六/周日） |
| `HOLIDAY` | 该日是法定休息日：周六/周日**且非**调休上班日，**或**是法定节假日 |

### 5.3 「跳过 N 个响铃日」的换算算法（核心）

```
输入：分组（或单个闹钟）的生效重复规则、N（默认 1）、当前时间 now
1. cursor = now 所在日期
2. count = 0
3. 循环：
     days = cursor 当天，该分组内所有启用闹钟中匹配 §5.2 且「时分 > now」的（仅 cursor == today 时需要这个时分判断）
     若 days 非空 → count += 1
     若 count == N → 恢复时刻 = cursor + 1 天的 00:00:00.000，结束
     cursor += 1 天
     （最多向后扫 400 天，防御性上限）
4. 落库：pauseUntil = 恢复时刻，pausedAt = now
```

**效果验证**（工作日组，每天 07:00）：

| 当前时间 | N | 跳过 | 恢复时刻 | 是否正确 |
|---|---|---|---|---|
| 周一 10:00（今早已响过） | 1 | 周二 | 周三 00:00 | ✅ 周二不响、周三照响 |
| 周一 06:00（今早还没响） | 1 | 周一 | 周二 00:00 | ✅ 今天请假，明天照响 |
| 周一 10:00 | 3 | 周二、三、四 | 周五 00:00 | ✅ 连休 3 天 |
| 周五 20:00 | 1 | 下周一 | 下周二 00:00 | ✅ 跳过周末，周六日因为本来就不响所以不计入 |

**关键设计取舍**：不在「响铃那一刻递减计数器」，而是**在操作瞬间就换算成绝对时间戳**。理由：

1. 判定逻辑退化成 `now < pauseUntil`，没有并发和状态消耗问题；
2. UI 能立即告诉用户确切的恢复时刻，所见即所得；
3. 设备重启、时间被改都不会让暂停状态错乱（`pauseUntil` 是绝对时间，时间被改后按 §5.4 重新校验）。

### 5.4 响铃时刻二次校验（可靠性核心）

闹钟被系统唤醒、**真正发声之前**，原生代码必须再查一次数据库：

```
若 闹钟已不存在（被删）            → 静默退出（不响、不重排）
若 闹钟.enabled = false            → 静默退出
若 闹钟.permanentlyDisabled        → 静默退出
若 闹钟.pauseUntil > now           → 静默退出
若 分组.permanentlyDisabled        → 静默退出
若 分组.pauseUntil > now           → 静默退出
若 计算出的本次响铃时间 != 本次触发时间 → 静默退出（防止旧的重复闹钟被重放）
否则                                → 进入响铃流程
静默退出时：无论哪种原因，都要重新计算并注册该闹钟的下一次
```

**为什么必须这么做**：`AlarmManager` 的取消注册存在竞态（暂停操作与触发几乎同时发生），而系统级的 pending intent 也可能因为重启/更新残留。二次校验把「暂停了却还响」的可能性压到接近零，代价只是一次本地数据库查询。

### 5.5 暂停状态判定优先级

从高到低（任一命中即不响）：

1. 闹钟已被删除
2. 闹钟 `enabled = false`
3. 闹钟 `permanentlyDisabled` / `pauseUntil > now`
4. 分组 `permanentlyDisabled` / `pauseUntil > now`
5. 本次触发时间与当前计算结果不符

### 5.6 一次性闹钟生命周期

```
创建（deleteAfterRing = 总开关的值，可覆盖）
  ↓
响铃 → 贪睡（至多 N 次）→ 关闭 / 超时自动停止
  ↓
deleteAfterRing == true  → 从数据库彻底删除，并取消其所有待触发注册
deleteAfterRing == false → 标记 expired = true，进入列表底部「已过期」区，不再参与调度
```

### 5.7 冗余触发策略

为防止单次触发丢失，每个闹钟注册**两个** `setAlarmClock`：

- 准点触发（主）
- 准点前 5 秒触发（冗余前锋，命中后走同一套二次校验；若主触发在 5 秒内也到达，二次校验会因「已进入响铃流程」而静默退出，不会响两次）

## 9. 风险与缓解

| # | 风险 | 影响 | 缓解措施 | 残留风险 |
|---|---|---|---|---|
| R1 | HyperOS 后台管控导致闹钟唤不醒进程 | 该响不响 | `setAlarmClock` + 前台服务 + 冗余触发 + 权限体检引导 | **无法消除**：用户手动「结束运行」后任何第三方 App 都无法唤醒。已通过 FR-5.6 文案告知 |
| R2 | 用户未授予自启动 / 电池无限制 | 该响不响 | FR-5 权限体检页 + 主界面常驻警示条 | 用户主观不授权则无解 |

## 12. 改名评估：「闹钟坞」→「时间管家」？

> 用户 2026-10-03 问：「项目改成叫「时间管家」如何？改动量是否大？（目前不用改，我想听听你的建议，可以进行对比）」
> 本节是评估与建议，**没有决定**。定了就写进 §10 决策点。

### 12.1 改动量（实测行数，不是估计）

| 层面 | 现在 | 要改的地方 | 规模 |
|---|---|---|---|
| **应用显示名** | `闹钟坞` | `res/values/strings.xml` 两处（`app_name` / `title_activity_main`）+ `README`、`PRD` 等文档里的 23 处 | **很小**，10 分钟 |
| **代码标识符** | `AlarmHub*` | `AlarmHubApp` / `AlarmHubPlugin` / `AlarmHubBridge`（契约接口名）/ `AlarmHub(Plugin)` 插件注册名 + 包 `com.alarmhub.app` + 前端 `bridge/types.ts` 接口名 + mock | **中等**：`AlarmHub` 命中 **669 行**、`com.alarmhub` 命中 **436 行** |
| **包名** | `com.alarmhub.app` | 目录 `java/com/alarmhub/app/`、`build.gradle` 的 `namespace`/`applicationId`、`capacitor.config.json`、`AndroidManifest`、全部 Intent action 字符串、`DebugReceiver` 的签名级权限 `com.alarmhub.app.permission.DEBUG`、数据库文件名 | **大且危险**：见下面三条代价 |
| **仓库名** | `AlarmHub` | GitHub 仓库名（可改，会换 URL） | 小 |

### 12.2 改包名的三条真实代价（这才是"大不大"的答案）

1. **手机上的数据会丢。** `applicationId` 一改，Android 认为这是一个**全新的应用** ——
   现有数据库、设置、权限授予**都不跟随**。用户手机上现在就装着旧版（1.0），
   要么手动迁移数据（导出/导入，而 PRD §1.4 **明确不做**备份导入），要么接受闹钟重设。
2. **调试通道要全部重配。** `DebugReceiver` 的签名级权限、`adb` 命令里的 action 名、
   `verify-phone.py` / `m3-acceptance.ps1` / `ui-drive.py` 里写死的包名都要改，且**真机验证要重跑一遍**。
3. **文档与验收记录里几百处引用会失真。** `STATUS.md` §1.1 那个 bug 台账、"之前实测过"的结论，
   全都在说 `com.alarmhub.app`；改完之后它们变成"关于另一个应用的历史"。

**只改显示名的代价 ≈ 零**（`strings.xml` 两行），**数据库和权限完全不受影响** ——
因为 `applicationId` 没变，Android 仍认为这是同一个应用。

### 12.3 名字本身值不值得换（我的看法）

| 维度 | 闹钟坞 | 时间管家 |
|---|---|---|
| 定位准确度 | **准**：产品就是"闹钟的停靠坞"（分组整组放假） | **偏大**："管家"暗示管**时间**——计时器、秒表、世界时钟、日程，而 §1.4 明确**不做**这些。名字比功能大，用户会期待落空 |
| 与"系统闹钟"的区分 | 有区分度 | 容易被当成"又一个时钟类 App"，反而更像要跟系统自带的比功能全 |
| 记忆成本 | 稍怪但独特 | 顺口、通用（也意味着**不独特**，同名应用更多） |
| 英文名 | `AlarmHub` 和中文名互相呼应（hub = 坞） | `TimeHub` / `TimeKeeper`？与现有 669 行标识符都要重来 |

**我的建议：不改名，或者只做最小改法。**

- **首选**：保持 `闹钟坞 / AlarmHub`，把力气花在真正影响体验的地方（比如 FR-7.10 的到点提示）。
- **如果你确实喜欢"时间管家"**：**只改显示名**（`strings.xml` 两行 + 文档），
  **包名和代码标识符一个都不动**。代价几乎为零，数据不丢，随时可以改回来 ——
  产品名和包名本来就不必一致（`applicationId` 只是技术标识，用户永远看不到）。
- **不建议**：现在连包名一起改。除了数据丢失，还会让 `STATUS.md` 里那份 25 条的 bug 台账
  与"当前应用"脱钩 —— 那是这个项目最值钱的东西之一。

> **给"时间管家"这个名字本身的一条意见**：如果将来真要扩到计时器/秒表，
> 那时改名才顺理成章（功能大了名字才该大）。**现在改是拿一个准确的小名字，换一个大而不准的名字。**
> 而按 §1.4，那些扩展功能是被明确排除的。
